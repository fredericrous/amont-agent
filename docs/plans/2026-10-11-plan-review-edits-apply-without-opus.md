# Plan-review edits apply without an Opus subagent

## Review panel

👉 **Decide:** none — approve if reviewers hand back patches, `plan-apply` applies them with no model, and a Sonnet-preferred, relais-routable subagent takes only the remainder.
📍 amont-agent, relais, dotfiles · plan reviewed, nothing built · next: Phase 1 `plan-apply` in an amont-agent worktree. Panel: backend (opus-5-5), lang:rust (opus-5-5), tui (opus-5-5), unix (opus-5-5).
**Changed by review:** `--check` tolerates `new_string` containing `old_string`; relais gets `record_merge_outcome` (the `router-observe` UPDATE needs a session the join lacks); patches resolve by the pre-apply sha from launches and resumes.
📄 Full reviews: [2026-10-11-plan-review-edits-apply-without-opus.reviews.md](2026-10-11-plan-review-edits-apply-without-opus.reviews.md)
**Verdicts:** round 1: 4 approve-with-changes; backend round 2: approve-with-changes ×3, then approve ×2 (the last on a fence fix); no rework; 12 findings carried into implementation.

## Context

On 2026-10-11 one plan review spent about 254k tokens on five reviews and about 320k on the four `general-purpose` subagents that applied their findings (the merge baseline: 320k per review, 80k per subagent): each one re-read the whole plan on the session's model (Opus) to turn prose `Edit:` instructions into edits, and a 15-line fix cost as much as a 60-line one. The reviewers already have the plan open and know the exact lines, so the edit can leave the reviewer as a patch pair and be applied by a command, with a model only for what does not match. Measured facts: reviewer agents share one output block (`Edit: <the concrete change to the plan>`); the amont-agent panel hook reads nothing below the `Verdict:` line (`src/review_outcomes.rs:238-250` reads only the verdict); relais rewrites a spawn's `model` only when routing is `on` and the table decides (`claude-plugin/hooks/routing.ts:383-385`), a `model:` front-matter key becomes a pin the router never touches (`crates/relais/src/router/state.rs:271-277`), and `relais native review-outcome` (source only, `crates/relais/src/main.rs:620-631`) already joins amont-agent ledger rows to router tasks by `agent_id` (`ledger/review.rs:106-116`).

## Goal

A review finding carries its own patch. `amont-agent plan-apply` applies the accepted patches with no model, reports what did not match, and writes a `merge` row to the plan-review ledger. What does not match is applied by the main session's `Edit` when it is small, else by one subagent that runs on Sonnet unless relais's router chooses otherwise, and whose outcome relais learns from. Expected: the merge step drops from about 80k per subagent to the ledger row plus the unmatched remainder.

## Non-goals

- `implementation-review.md` keeps its contract: its edits are code, applied by the session in a worktree.
- No change to the panel composition, the round bound, the hook's pass rules, or `plan-review record`'s row schema (a `merge` row is a new `schema` value in the same file).
- No cheaper-model exploration for reviewers (the ledger plan's Phase 8).
- No change to `work.findings-one-per-line`: findings stay one line; patches sit in a separate fenced block after them.

## Behaviour

1. **Reviewer output** (11 `plan-review-*.md` agents, one shared block). After `What I would measure:`, a final section:
   ````
   Patches:
   ```json
   [{"finding": 1, "old_string": "<exact text from the plan, unique>", "new_string": "<replacement>"}]
   ```
   ````
   (A four-backtick outer fence, as CommonMark requires around a three-backtick one: with equal fences, `plan_review::canonical`'s tracker closes on the inner fence and reads the rest of the plan as code, so `## Full reviews` is never stripped and the body sha follows the review text — observed on this plan on 2026-10-11. The agents' own template uses the same.) One object per finding that proposes an edit, `finding` matching the finding number; a finding with no edit (a 👉 decision, a `carried` note) has no object. `old_string` is copied from the plan verbatim and must occur once; a reviewer that cannot make it unique widens it to the surrounding line(s). Several edits for one finding are several objects. The 350-word limit excludes this block. Round-2 and delta reviews carry patches the same way. `old_string` and `new_string` are JSON strings, so a code fence inside them is fine (a patch to this section's own fenced example carries one); an empty `old_string` is never valid.
2. **`amont-agent plan-apply <plan.md>`** (amont-agent, new `src/plan_apply.rs`, registered like `plan-review` in the `SUBCOMMANDS` table at `src/main.rs:149-168`, which becomes `[(&str, Sub); 20]`, returning `(String, ExitCode)` so `main` prints). Stdin: a JSON array of accepted findings `[{"role": "tui", "finding": 1}, …]` (or `{"role": "tui", "finding": 1, "patch": {...}}` to supply a patch the main session wrote itself); stdin on a TTY is exit 2 with usage. The patches come from the transcript, as `record` does: `plan_review::completed_agents` (it filters by agent type) on the review block prefix gives each role's result text, taken from the LATEST completion of that role, launch or `SendMessage` resume (`plan_review::completed_agents_resumable`, `src/plan_review.rs:721`, since round-2 reviews are resumes), whose review-block sha equals the plan's body sha BEFORE this apply: the current sha for a plain apply, and for `--check` and `--record-fallback`, which run after the plan was written, `body_sha_before` from the `<<<APPLY … sha=…>>>` block (`--record-fallback`) or from the latest `mode: "command"` merge row for this `plan_path`, overridable with `--before <sha>` (`--check`). Both merge rows store the full 64-hex `body_sha_before`; the APPLY block and `--before` carry a prefix of at least 12 hex, matched as a prefix of the launch sha, and a prefix matching two distinct launch shas is exit 1 `ambiguous --before`. The `Patches:` fenced block is parsed from the selected result. Phase 1 tests: apply, edit the plan, then `--check` still resolves the patches (exit 0, not 1); round-2 patches resolve from a resume (fixture `tests/fixtures/sendmessage-resume.jsonl`).
   - **Fenced-block parsing.** After `Patches:` and the opening fence, parse with `serde_json::Deserializer::from_str(rest).into_iter::<Value>().next()` and ignore the closing fence, because a patch to a fenced section (Behaviour 1) carries a fence inside the JSON string.
   - **Matching, applied in stdin order.** `old_string` must occur exactly once in the current file text; occurrences are counted with `match_indices` (non-overlapping, documented). Offsets from `str::find` are char boundaries, so slicing is UTF-8 safe (stated in a doc comment). Applied ranges are tracked as `[start, start+new.len())` in current-text coordinates; a later patch overlaps iff `s < end && s+old.len() > start`, reported `unmatched: overlaps <role>#<n>`. On a 0-match, retry on a whitespace-normalized copy (CRLF to LF, trailing whitespace trimmed) ONLY to label the reason `absent (whitespace)`; never apply from the copy. An `old_string` found in a region `plan_review::canonical` strips (front matter, `## Review panel`, `## Full reviews`) is applied but reported `outside the body`. An empty `old_string` is a usage error (exit 2). A 0-match or many-match patch is `unmatched: absent` / `unmatched: 3 occurrences`.
   - **Write rule (one rule).** Matched patches are written, unmatched ones are listed; the file is written once through the crate's atomic write (`src/atomic.rs`). `shas(new)` is computed BEFORE the write; on `ParserPanicked` the file is still written, the row records `body_sha_after: null`, and stderr says `sha unavailable`.
   - **Concurrency and links.** The ledger `Lock` is taken before the plan is read. Just before `write_atomic`, the file is re-read and compared byte for byte with the first read; if they differ, exit 1 with `plan changed under plan-apply; nothing written`. The plan path goes through `fs::canonicalize` and the write targets the result, so a symlinked plan keeps its link.
   - **Output.** Per-finding lines and the summary are data on stdout; diagnostics go to stderr (`cli.basics.stdout-is-data-stderr-is-talk`, as `record` does). Each line is at most 80 columns (long role or section names truncated); the leading words `applied`/`unmatched` carry the meaning, never colour. Lines: `applied tui#1 Behaviour` / `unmatched tui#3: absent` (section = nearest heading above the match), then `applied A, unmatched U, sha <plan-sha --short of the new text via plan_review::shas>`. On exit 3 a last line follows the unmatched lines: `next: apply the unmatched edits, then run amont-agent plan-apply --check <plan>`. The `<<<APPLY path=… sha=…>>>` block is printed LAST on stdout after a blank line; it is the only multi-line stdout record, may exceed 80 columns because it is machine-read, and is shown in `--help`.
   - **Missing or malformed Patches block.** Distinct messages and exit 3 per reviewer: stderr `plan-apply: tui result has no Patches block; apply its Edit lines by hand, then run plan-apply --check`, and the role's findings are listed as `unmatched tui#1: no patches block` / `unmatched tui#1: patches block is not JSON`.
   - **Exit codes.** 0 when U = 0; 3 when some patch is unmatched (the file changed when A > 0; 3 is new to the crate); 1 for file I/O (read, write, concurrent change) and when no transcript holds the reviewer's result; 2 usage. `--dry-run` reports without writing.
   - **`--check`.** Takes the same stdin, writes nothing, and passes when each `new_string` occurs exactly once AND `old_string` is absent (the absence test is required only when `new_string` does not contain `old_string`); an empty `new_string` requires only `old_string` absent. Exit 0 verified, 3 not verified, 1 I/O or no transcript, 2 usage. It is the verifier for the fallback.
3. **`merge` row.** `plan-apply` appends to `plan-review/outcomes.jsonl` (reusing `review_outcomes::{lock, open_ledger, private_options}`, made `pub(crate)`; `Lock` itself becomes `pub(crate)` with `lock()`, since a private return type would trip `private_interfaces` under clippy `-D warnings`) one row `schema: amont-agent-review-merge-v1` with `recorded_at, plan_path, body_sha_before, body_sha_after, round, accepted, applied, unmatched (list of role#n: reason), mode: "command"`; `round` is derived from the launch the patches came from (Behaviour 2). `recorded()` (`src/review_outcomes.rs:341`) today collects `agent_id` from every row: it gains a `schema == "amont-agent-review-outcome-v1"` filter, with a test, so merge rows never enter the review dedupe set. Exit 3 is new to the crate: it is added to the exit table in `docs/plan-review.md`, with a one-line doc touch in `src/atomic.rs` (its module docs say settings.json only). After the fallback (item 4) runs, `amont-agent plan-apply --record-fallback <plan.md>` scans the transcript for the fallback launch (found among `general-purpose` launches, filtered by a prompt starting with the block `<<<APPLY path=<plan> sha=<sha12-before>>>>`, printed by `plan-apply` on exit 3), runs the `--check` logic on the findings it was given, and writes a second row with `mode: "subagent"`, `agent_id, model, tokens, seconds`, and `verified: true|false`. It exits 0/1/2 like `record`, dedupes on (`schema`, `agent_id`) under the `Lock` (a rerun writes nothing), and a failure between the plan write and the ledger append exits 1 with stderr `plan written, merge row not`. That row is what relais ingests.
4. **The skill's step 4** (`~/.claude/skills/plan-review/SKILL.md`, chezmoi source `dot_claude/skills/plan-review/SKILL.md`; the installed copy is ahead of the source by the `record` bullet and the model-in-panel-line wording — the source is brought level first, in the same change). After `plan-review record`: pipe the accepted lines to `plan-apply`. On exit 3: when the unmatched findings number at most 3 and each proposed edit is under about 15 lines, the main session applies them with `Edit` (the old and new text cost less than a subagent's read of the plan); otherwise launch ONE `general-purpose` subagent in the foreground with `model: "sonnet"`, whose prompt carries the `<<<APPLY …>>>` block first, the unmatched findings verbatim with their evidence and edit, and ends with "run `amont-agent plan-apply --check <plan>` with the findings on stdin as the last command; return its output only". Then `plan-apply --record-fallback`. The `sonnet` on the call is a preference: relais's router leaves it when routing is off or abstains, and overrides it when routing is on and its table decides (`routing.ts:383-385`), which is wanted — no `model:` pin, so the spawn stays routable. Step 5's round-2 prompt tells reviewers that their round-1 patches were applied by `plan-apply` where they matched.
5. **relais ingest.** `relais native review-outcome` also reads `amont-agent-review-merge-v1` rows with `mode: "subagent"` and an `agent_id`: `Ledger::router_task_for_agent(agent_id)` gives the router task; a `verified: true` row applies a `task_outcome` of `completed_verified`, `false` applies `corrected`, through a new writer. The `router-observe` UPDATE cannot be reused: it keys on `session AND task_id AND agent_id` and hardcodes `outcome_source='parent'` (`ledger/router.rs:562-566`), and `router_task_for_agent` returns only `task_id`. Phase 3 adds `Ledger::record_merge_outcome(task_id, agent_id, outcome, rank)`: `UPDATE router_tasks SET outcome=?, outcome_source='merge' WHERE task_id=? AND agent_id=? AND outcome='unknown' AND outcome_rank < ?`, with the ranks of `completed_verified` and `corrected` from `router/outcome.rs:46`. `relais report --json` gains the merge counts. Rows without an agent id (mode `command`) are counted and skipped. Unknown schemas stay skipped, as today. The report line gains `merge: N applied by command, M by subagent (V verified)`.

- 2026-10-11 — `plan-apply` reads patches from the transcript, not stdin: the main session then passes only `{role, finding}` and never re-sends the old and new text, which was the cost the skill's step 4 already names.
- 2026-10-11 — the fallback subagent gets `model: "sonnet"` on the call and no `model:` pin: a pin would take it out of relais's routing and its outcome; a call-level model is a preference the router may override.
- 2026-10-11 — the subagent's outcome reaches relais through the amont-agent ledger it already ingests, not through a new relais command: `router-observe` needs session, task and agent ids nothing outside the plugin has, while `review-outcome` already joins by agent id.
- 2026-10-11 — a relais `run` is not used for the fallback: its `write_scope` is repo-relative inside a worktree, and the plan lives in `~/.claude/plans/` until it lands.

- 2026-10-11 — stdout is data (`cli.basics.stdout-is-data-stderr-is-talk`); the `<<<APPLY …>>>` block is the one multi-line stdout record. A `--quiet` flag (tui's proposal) is rejected: the exit code already carries the result.

## Outcome

Shipped 2026-10-11: amont-agent 2.36.0 (#98, #99), relais#207, dotfiles#31. Measured 2026-10-12 on the first three real reviews run with the new skill (14 merge rows, 36 review rows):

- **Match rate** (reviewer patches applied ÷ proposed): 97 applied, 14 unmatched, **87.4 %** — above the 70 % floor. Per plan 97.8 %, 76.6 %, 89.5 %. Unmatched by reason: 9 `overlaps` (two reviewers editing the same lines), 5 `absent` (an `old_string` not copied verbatim).
- **Merge tokens**: one Sonnet fallback subagent in three reviews, 107k; **36k per review, 11 % of the 320k baseline** — under the 25 % ceiling. Two of the three reviews needed no subagent at all; the remainders were 8 person patches applied through `plan-apply`.
- **What surprised**: the one fallback cost more than a baseline Opus subagent (107k vs 80k) and its `--check` came back `verified: false` on all 12 patches it was given (`new_string occurs 0 times`): those were the overlapping patches, which a subagent resolves by writing one merged edit, so the reviewers' literal `new_string` never appears. That `false` reaches relais as `corrected`, a false negative. The fix belongs to a later change: `--check` could accept a patch whose `old_string` is gone when it overlapped another applied one, or the skill could hand overlapping patches to the session as one person patch instead of to the subagent.
- Review cost itself (not this plan's target) stayed at 40–60k per reviewer: 842k, 634k, 249k for 14, 16 and 6 reviews.
